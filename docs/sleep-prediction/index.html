nuggi · src/lib/sleep/predict.ts

How Nuggi guesses the next nap

No machine learning, no server call. Start from what's typical for the baby's age, lean more on the baby's own logged rhythm the more of it there is, then count forward from the last time the baby woke up. The same inputs always give the same answer, and every step writes a line into the “Warum?” (“why?”) panel on the Heute screen.

Overview

The whole pipeline on one page

Step 1 · priors.ts

Start from what's typical for the age

The baby's age in completed weeks picks one row. The midpoint of the wake window range is the starting guess; nap count and length feed into bedtime and the nap duration.

BracketFrom wkWake windowMidpointNapsNap lengthClamp range

Clamp range = 0.8 × min … 1.2 × max. The prediction can never leave it, however odd the logged data looks.

Step 2 · observe()

Measure the baby's own rhythm

Finished sleeps from the last 7 days are sorted by start time. The gap between one sleep ending and the next starting is one wake window. Night wakings don't count, and neither do implausible gaps.

Counts as a wake window

A gap of 10 min to 8 h between two logged sleeps. A night→night gap that ends inside the night window (default 19:00–07:00) is a night waking and is skipped.

Counts as a nap length

A sleep tagged nap lasting 5–240 min.

Trimmed median

Sort, drop the top and bottom 10 % (rounded down), take the median. One skipped nap or a 20-minute catnap can't pull the result much.

Step 3 · blendWeight()

Trust the baby more as the data grows

With n observed wake windows, the observed median gets weight w and the age prior gets 1 − w. It starts after 2 observations and tops out at 70 %, so the age norm always keeps at least 30 % of the say.

w = min(0.7, max(0, (n − 2) / 8)) window = (1 − w) · prior_mid · position + w · observed_median window = clamp(window, 0.8 · min, 1.2 · max) // rounded to whole minutes

The same n sets the confidence label shown on the ring: under 3 is niedrig, 3–9 mittel, 10+ hoch. Nap length uses the identical blend on its own count, clamped to 0.6–1.6 × the prior nap length.

Step 4 · positionFactor()

First window shorter, last one longer

Babies usually manage less awake time right after the night and more before bed. The prior part of the blend is scaled by where in the day the upcoming gap sits, counted by naps already done today (a nap in progress counts as done).

Step 5 · anchor

Count forward from the right moment

The next nap is anchor + wake window, shown as a window of ±15 min around it. Which anchor depends on the current state:

asleep · napPredicted wake-up

Nap start + nap length (at least now + 5 min). The following window counts from there.

asleep · nightNight end

Wake-up is the configured night end (07:00 by default); tomorrow's bedtime is shown.

awakeLast sleep ended

Used if it ended within the last 16 hours.

no dataAssumed wake-up

Night end, or “now” if it's still before that. The reasoning says so explicitly.

Step 6 · bedtime

Bedtime bends toward the target, but only so far

bedtime = max(lastNapEnd + lastWindow, target − 45) bedtime = clamp(bedtime, target − 60, target + 45) if daytime naps today > expected + 30 min → bedtime +15 if daytime naps today < expected − 45 min (after target − 3 h) → bedtime −15 if nextNap > bedtime − napLength / 2 → no more naps: next sleep is bedtime

The light band is where the formula normally lands; the darker edge down to target − 60 is only reachable via the “little daytime sleep” adjustment. Expected daytime sleep = average naps × prior nap length (3.5 × 45 = 158 min at 3–4 months).

Simulate a day

This runs the same formulas as predict(): wake at 07:00, bedtime target 19:00, every nap taking exactly the predicted length. It leaves out the ±15 min daytime-sleep nudge. Starts with a 4-month-old who has 12 logged wake windows.

    Bonus

    Feeds use a plain interval

    Next feed = last feed start + interval. The interval is the family's setting, otherwise by age: 150 min up to 4 weeks, 180 up to 12, 210 up to 30, then 240. The push reminders cron reads the same Prediction object, so the ring and the notifications never disagree.
